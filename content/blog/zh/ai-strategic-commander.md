你玩过动作游戏吗？就是那种你控制一个英雄，一个怪一个怪地打的那种。怪物挡在路上，你就得亲自动手，一刀一剑地把它砍死。打完这个，下一个。打完下一个，再下一个。每一场战斗，都需要你全神贯注。

现在大部分人和AI合作，其实就是在玩这种动作游戏。

你给AI一个任务，AI开始执行，你全程盯着。AI卡住了，你介入指导。AI完成了，你检查结果。然后你再给下一个任务，继续盯着。循环往复。

这有什么问题吗？

# 现实项目更像战略游戏，不像动作游戏

问题在于，现实世界的复杂项目根本不是动作游戏。

动作游戏的关卡是设计好的，你只需要顺着路走下去。但真实的项目呢？你面前是一片迷雾，你甚至不知道该往哪个方向走。

![](/blog/ai-strategic-commander/fig-01.png)

你玩过星际争霸或者红警吗？那是即时战略游戏。游戏开始的时候，整个地图都被"战争迷雾"笼罩着。你看不到敌人在哪，不知道资源在哪，不清楚哪条路能通。

你不可能亲自去每个角落侦察。你能做的，是派出侦察兵。东边派一个，西边派一个，北边再派一个。这些侦察兵各自出发，各自探索，然后把发现带回来告诉你。

侦察兵A说："东边有一片矿区。"侦察兵B说："西边是死路，过不去。"侦察兵C说："北边发现敌人基地了。"

这时候你才开始真正做决策：是先去采矿，还是绕开西边，还是集中兵力打北边？

这，才是你和AI合作的正确姿势。

# 官方实现了，不用写脚本

之前我写过两篇关于Ralph Loop的文章。

第一篇“[睡觉的时候让AI不停地干活？把AI困在无限循环的牛马噩梦里](/zh/blog/ralph-loop-ai-nightmare)”，讲的是怎么让AI困在循环里自己干活。

第二篇，“[除了增强AI，Ralph Loop也能用来提高人类的效率？用认知科学解读 AI 协作的最优模式](/zh/blog/ralph-loop-human-efficiency)”，讲的是这种工作方式对人类的好处。

核心思想很简单：把规划和执行彻底分开，让人类专注战略思考，让AI负责具体探索。道理都懂，但很多朋友看完之后打了退堂鼓。打开教程一看，满屏幕都是命令行、配置文件、环境变量。算了，改天再说吧。

![](/blog/ai-strategic-commander/fig-02.jpg)

好消息是，Anthropic官方下场了。Claude Code现在内置了一套叫做Tasks的机制，核心理念和Ralph Loop一模一样，但你不需要写一行脚本。

# 每个任务都有独立的脑容量

要理解这套机制，首先得理解一个关键问题：AI的脑子会越聊越乱。

想象一下，你和AI聊天的过程就像往一个箱子里不停塞东西。你问一个问题，塞进去。AI回答，塞进去。你让AI读一个文件，塞进去。AI尝试了一种方法失败了，那个失败的过程也塞进去。

问题是，这个箱子只能装东西，不能往外拿。

Geoffrey Huntley有一个很精准的比喻。他说，在传统编程里，你用malloc申请内存，用完了可以free释放掉。但在和AI对话的时候，信息只进不出。失败的尝试、无关的文件内容、之前聊过的话题，全都堆在那里。AI的脑容量就那么大，这些没用的东西占着位置，让AI越来越难专注于当前的任务。

这就是为什么很多人觉得和AI聊久了，它变得越来越"笨"。不是它真的变笨了，是它的脑子被之前的垃圾信息塞满了。

Ralph Loop的解决方案是什么？不停地重启。每次重启都清空上下文，让AI用全新的脑容量来处理当前这一件事。

Claude Code Tasks的思路也是一样的，只不过更优雅。它引入了一个叫Subagent的概念——你可以把Subagent理解成Claude派出去的"分身"。每个分身都有自己独立的脑容量，独立的工作空间，互不干扰。

# 项目是一棵树，不是一条线

现在来聊聊这套机制真正强大的地方。

很多人理解Tasks，只是理解到"可以同时派多个AI去探索不同方向"。这没错，但只说对了一半。

一个真实的项目，不只是有"不同的方向"，还有"不同的步骤"。

比如你要做一个产品，大概要经过这么几步：调研需求、设计方案、开发实现、测试验证。这些步骤是有先后顺序的——你不可能在需求都没搞清楚的时候就开始写代码。

但问题是，每一个步骤里面，又有好几种可能的方案。调研需求的时候，你可以从用户访谈切入，也可以从竞品分析切入，也可以从数据分析切入。设计方案的时候，可能有技术路线A、技术路线B、技术路线C。

这样一来，整个项目就变成了一棵树。

![](/blog/ai-strategic-commander/fig-03.jpg)

树的第一层是"调研需求"，下面分出三个分支：用户访谈、竞品分析、数据分析。树的第二层是"设计方案"，但这一层要等第一层完成了才能开始，而且第二层的分支可能取决于第一层的结果——如果竞品分析发现了一个很好的参考，第二层的分支可能就会围绕那个参考来展开。

每一个"节点"，其实就是项目某个步骤的某个具体方案。而整个项目的探索过程，就是在这棵树上不断往下走，直到找到一条能走通的路径。

# 依赖关系：让AI知道先后顺序

Claude Code Tasks有一个特别关键的功能：任务之间可以设置依赖关系。

什么意思呢？你可以告诉Claude："任务B依赖于任务A，所以在任务A完成之前，不要开始任务B。"

这个功能看起来简单，但意义重大。

有了依赖关系，你就可以在项目开始之前，把整棵树的结构都规划好。第一步要做什么，有哪几个可能的方向；第二步要做什么，依赖于第一步的哪些结果；第三步又依赖于第二步的哪些结果……

规划完成后，你把这棵树交给Claude Code。它会自动按照依赖关系来安排执行顺序：先跑第一层的所有任务，等第一层完成了，再根据结果启动第二层的任务。

你不需要盯着每一步的进度。你只需要在关键节点——比如第三层的方案C效果最佳，但第四层的方案B卡住了的时候——再回来看看结果，决定下一次迭代要从这里开始深入。中间没什么问题的结果就直接跳过。

# 不只是写代码

有人可能会说，Claude Code不是一个编程工具吗？我又不是程序员，这和我有什么关系？

其实Claude Code能做的事情多了去了。它叫"Claude Code"只是历史原因。

你可以用它做市场调研，让多个Subagent同时去分析不同竞争对手的资料。你可以用它写文章，像刚才那个例子一样，把调研、选角度、写大纲、填内容变成一棵有依赖关系的任务树。你可以用它做数据分析，让它帮你处理Excel表格、生成图表、写分析报告。你甚至可以用它来做图片，它能调用各种图像生成API帮你出图。

本质上，任何需要"探索-尝试-迭代"的任务，都适合用这种方式来处理。只要你的项目可以拆成步骤，每个步骤又有几种可能的方案，你就可以把它变成一棵树，然后让AI去探索这棵树的每一个节点。

# 这种方式和手把手有什么区别

手把手的方式是线性的。你完成一步，检查一步，然后再进行下一步。你的注意力完全被占用，没法思考更大的问题。而且你一次只能走一条路——如果这条路走不通，你得退回来从头再试另一条。

而"树状探索"的方式完全不同。

你在顶层把整棵树的结构规划好，然后一次性交给AI。AI会自动处理依赖关系，自动并行执行可以并行的任务，自动等待需要等待的任务。你不需要全程盯着每一个细节，你只需要在关键节点做决策。

更重要的是，这种方式能帮你发现你原本想不到的东西。当你手把手教AI的时候，你只能走你已经想好的路线。但当你派出多个侦察兵去同时探索多个方向的时候，它们可能会发现你根本没想到的可能性。"老板，我在任务1C里发现了一个特别有意思的教师反馈，这个角度之前完全没人写过！""老板，任务3Y的大纲比我们预想的要顺畅得多，建议直接用这个方向！"

这些意外的发现，往往比你原本计划的路线更有价值。

# 今天就可以试

下次你用Claude Code的时候，别急着告诉它具体怎么做。先退一步，把你的项目画成一棵树。

想想：这个项目分成哪几个步骤？每个步骤有哪几种可能的方案？哪些任务可以并行，哪些任务必须等前面的完成？

然后这样说："我要做一个项目，分成三个阶段。第一阶段有三个并行任务……第二阶段的任务依赖于第一阶段的结果……帮我按这个结构来执行，每完成一个阶段就汇报一下进展。"

试试看。感受一下从"动作游戏玩家"变成"战略游戏指挥官"的感觉。

你会发现，你的大脑突然轻松了很多。那些琐碎的探索和试错不再需要你全程关注。你可以把注意力放在更重要的事情上：规划整棵树的结构、在关键节点做决策、综合各路情报形成全局判断。

这需要练习。你需要学会把一个模糊的目标拆成步骤和方案，需要学会判断哪些任务可以并行、哪些必须串行，需要学会从AI带回来的零散情报中拼出完整的地图。

但这是值得练习的技能。因为这不仅是使用AI的最佳方式，也是应对复杂世界的最佳方式。

真正厉害的人，从来不是事事亲力亲为的人。而是懂得把问题变成一棵树，然后调动资源去探索这棵树的每一个节点，最后综合情报做出决策的人。

现在AI给了你这样一支随叫随到的侦察兵队伍。用好它。

下次遇到复杂问题的时候，别急着一头扎进去。退一步，画一棵树。然后让AI替你去探索每一个节点。

你负责看地图，做决策。
